# Local DAT worker disabled at `/email-quotes`

## Triage status

- Status: `TRIAGED`
- Date: 2026-08-12
- Client: First Class Trucking
- Environment: local development (`http://localhost:3000` client and `http://localhost:3001` API)
- Affected surface: CRM Quote Inbox DAT RateView card and approval path
- Primary classification: `environment`
- Confidence: high
- Recommended next owner: local CRM/DAT configuration owner (David Castillo / Optimation AI), followed by `reliability_qa` after configuration-only remediation

## Incident statement

The local CRM shows `DAT worker is not enabled on the server.` because the running local API does not have `DAT_WORKER_ENABLED=true`. The local API also lacks a configured DAT worker secret, the First Class automation has no local `.env`, and no DAT worker process is running. These are mutually consistent configuration and process-state failures introduced after the local environment file was last updated.

The message is generated by the CRM API before a DAT job, Playwright browser session, or DAT network request is attempted. No evidence supports UI drift, authentication, permissions, client data, dependency, network, rate limit, or business-rule change as the primary cause.

1. `client/.env` configures the standalone development client to call the API at host `localhost`, port `3001`. No value beyond protocol, host, and port was retained in this report.

4. A separate key-presence inspection of `server/.env` found neither `DAT_WORKER_ENABLED` nor `DAT_WORKER_SECRET`. The file's modification time is 2026-08-04, before the DAT worker integration commit.

6. A read-only request to the running local API at `/api/dat-worker/status` returned HTTP 503 with `DAT_WORKER_SECRET is not configured`. This endpoint rejects the request in route middleware before attempting a database query.

9. `server/.env.example`, the repository README, and the automation README document the missing local configuration contract: the API needs `DAT_WORKER_ENABLED=true` plus a server-only worker secret; the worker needs the same secret and a CRM base URL.

## Cause classification

Primary cause: `environment`.

The local server and worker configuration required by the 2026-08-11 DAT integration was never added to the local runtime, and the worker is not started. The application is behaving as coded: an absent enable flag disables DAT preparation, and an absent worker secret disables the secured worker routes.

This is not classified as:

- `UI drift`: the error is emitted before Playwright or DAT UI access.
- `authentication`: the DAT session was not reached, and no worker is running to report `needs_auth`.
- `permissions`: no authorization or role failure was observed.
- `client data`: quote data cannot make the current process-level enable check pass.
- `dependency`, `network`, or `rate limit`: no DAT dependency or request was attempted.
- `business-rule change`: the approved workflow still expects the separately configured worker queue.

## Blast radius

- All quote records rated or re-rated through the running local API while the flag is absent receive a `disabled` DAT placeholder.
- Staff cannot create a DAT job through the local approval action; the server guard rejects it with HTTP 503.
- Existing local records may continue to display a persisted disabled placeholder until they are re-rated after configuration is corrected.
- Connected carrier rating remains available by design; this is not a whole-CRM outage.
- Production and Railway are outside this triage's inspection scope. No inference about their current health is made from local state.
- No evidence shows that a DAT lookup, lane credit, booking, posting, message, purchase, deletion, or account change occurred during this incident.

## Safe workaround

- Continue using connected carrier rates in the local CRM.
- If a DAT benchmark is operationally required before local repair, use only the already-approved human RateView procedure and record the result according to client policy. Do not automate credentials, MFA, CAPTCHA, or repeat an uncertain lookup.
- Do not repeatedly click the local DAT approval action. It cannot create a job while the flag is absent, and there is no worker to consume one.
- If local DAT operation is intentionally out of scope, treat the disabled card as expected local behavior and use the configured hosted non-production environment for authorized validation instead.

## Smallest proposed repair scope

No implementation patch is indicated. The smallest repair is local configuration and process startup owned by the local technical operator:

1. Decide explicitly that this workstation is an authorized non-production DAT worker environment.
2. Configure the local API with `DAT_WORKER_ENABLED=true` and a nonempty server-only worker secret.
3. Configure `clients/first-class-trucking/automation/.env` with the same secret, the local CRM base URL, an external persistent DAT browser-profile directory, and a distinct worker ID. Never place the secret in `client/.env` or any `REACT_APP_*` variable.
4. Restart the local API so `dotenv` loads the new values.
5. Complete `npm run auth` manually for DAT login/MFA/CAPTCHA, then start `npm run worker`. Authentication must remain a human takeover; no credentials should be written into the repository.
6. Re-rate only the affected synthetic or approved local quote so a persisted disabled card is regenerated. Do not bulk-update records.

This report does not perform any of those changes, generate or rotate a secret, modify permissions, start the worker, or operate on production.
