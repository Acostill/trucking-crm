# Stage 3 QA test matrix

Status: test design only; no cases have been executed.

Approved source: `discovery/workflow-spec.json`, workflow `fct-dat-rateview-lane-pricing`, version `0.3-approved-no-daily-cap`. Client facts and constraints are taken from the approved `intake/client-profile.json` and `intake/decisions.md`. Browser findings may supply observed locators and state setup later, but they must not change the business or safety oracles below.

## Test controls

- Use only fictional shipment data in the client-authorized DAT production RateView scope. Credentials, SSO, MFA, CAPTCHA, and reauthentication remain human-controlled.
- Treat the local ledger's `America/New_York` submitted-search count as audit-only and shared across discovery, QA, and operation. It must never block an otherwise authorized unique lookup or be reset, deleted, or relabeled to hide usage.
- Before every case, record the redacted run ID, test ID, workflow version, request ID, current day, duplicate state, and audit-only submitted-search count. Do not log lane values or authentication material.
- A case marked `0` credits must stop before `RV-080`. A case marked `0 if reused` must use an already completed result and must not open or submit DAT. A case marked `1 possible` or `1` may run only after duplicate protection and per-search human approval pass. DAT's own subscription, credit, rate, and usage controls always remain in force.
- Isolate cases with unique request IDs and idempotency keys. The only exceptions are the duplicate/rerun cases, which deliberately reuse a named setup key. Never reuse an uncertain or submitted key for a new search.
- Preserve the trace, screenshot, ledger, and safe-log evidence needed by each case, but retain only redacted QA evidence permitted by the 30-day screenshot/log rule. Functional ledger/result records may contain only the approved workflow fields and must not be copied into QA evidence unredacted. Never store passwords, tokens, cookies, MFA recovery codes, Playwright storage state, or raw sensitive exports.
- A live state that cannot be induced safely (for example, a subscription denial or a post-submit authentication loss) may be exercised only through an implementation-supported controlled state that preserves the same ledger and no-resubmit behavior. It is not acceptable to weaken the oracle or fabricate a pass. If neither a safe controlled state nor an authorized natural state exists, record the case as blocked.

## Release sequence and lookup accounting

1. Coordinate with discovery and operations, then read the shared ledger before scheduling QA. Record the current `America/New_York` submitted-today count for audit only; do not use it as an application limit.
2. Execute all applicable zero-credit cases first. A zero-credit case that unexpectedly reaches `RV-080` is a failed case and its lookup must still be counted.
3. Schedule no-rate, post-submit uncertainty, slow-result, extraction-failure, and partial-finalization cases in separately authorized windows when needed. Each may consume a vendor lane credit even when the expected outcome is a safe failure; DAT's own account controls must never be bypassed.
4. Run `QA-035` with five distinct fictional requests and explicit per-search authorization. Do not clear or backdate the ledger between runs; isolation comes from unique request IDs and keys.
5. After any failure in the consecutive sequence, reset the streak to zero. Continue only with fresh explicit approval for the next unique search; no application daily cap applies.
6. A duplicate-return assertion may reuse a result from the sequence, but it earns no consecutive-pass credit because it performs no read-only RateView search. Controlled-state/unit coverage also does not count toward the five live consecutive searches.
7. Release requires `QA-035` plus all applicable critical and failure-path cases above, zero unresolved release-blocking defects, and preserved redacted evidence. A safely uninducible critical state is `BLOCKED`, not passed by assumption.

## Explicit non-applicable workflow paths

The approved workflow contains no upload or download step and produces no authorized raw export. Upload/download execution tests are therefore out of scope; an unexpected download or export attempt fails `QA-033`. No popup or frame behavior is approved yet, so undocumented popup/frame behavior is handled conservatively by `QA-019` as UI drift rather than treated as a supported path.
